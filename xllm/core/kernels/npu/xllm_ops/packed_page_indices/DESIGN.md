# 设计说明：PackedPageIndices

## 1. 要解决的问题

连续批处理里，每个请求的页表只有前 `cu[r+1]-cu[r]` 项有效。下游的变长注意力与缓存组件需要一份紧凑的物理页号数组：请求依次排列，每个请求内部连续，负值表示空页。

一次调用完成三件事：

1. 只取有效前缀，跳过每行尾部；
2. 负页号翻成 -1；
3. 按层查映射表，得到物理页号。

## 2. 契约

输入：

| 名称 | 形状 | 类型 | 约束 |
| --- | --- | --- | --- |
| `X` | `[R, C]` | int32 | 连续、NPU、允许非零 storage_offset |
| `M` | `[B]` 或 `[L, B]` | int32 | 非负、同一设备 |
| `cu` | `[R+1]` | int32 | `cu[0]=0`，非递减，`0 ≤ cu[r+1]-cu[r] ≤ C` |

输出：`P = cu[-1]`，单层 `[P]`，逐层 `[L, P]`，独立连续 int32。

```text
out[l, cu[r] + j] = -1            if X[r, j] < 0
out[l, cu[r] + j] = M[l, X[r, j]] otherwise,  0 ≤ j < cu[r+1] - cu[r]
```

前置条件与违约处理：

- 输入个数、属性为空、NPU、int32、连续、同设备：Python 入口检查，抛 `TypeError` 或 `ValueError`。
- `cu` 单调性、每段不超过 `C`、`M` 非负、有效前缀页号小于 `B`、元素总数不超过 `2^31-1`：主机侧 C++ 检查，错误转成 `ValueError`。
- 无效尾部不参与值域检查，也不被设备读取。

后置条件与不变式：

- `prepare` 冻结形状、类型、设备与总 `P`；同形状的 `set_` 重绑定与总 `P` 不变的有效页数变化，下一次 `run` 必须观察到。
- `run` 每次返回新的连续输出，不修改输入，不使用默认 stream。
- 输出与输入不共享存储。

## 3. 数据流

```text
X, M, cu (NPU)
   │  prepare
   ├─ Python：设备 / 类型 / 连续性 / 维度检查
   ├─ CPU 副本 ──► C++ plan：值域、cu、P、L、B、2^31-1
   └─ Triton 计划：形状、网格、编译核、直接启动器
          │  run
          ├─ torch.empty(输出)
          ├─ 读当前 stream
          └─ 编译核 launcher(x, m, cu, out, C, B, P, R)
```

主机侧只决定“做什么”，设备核只决定“怎么做”。`run` 不做任何校验分支与元数据查询，只有一次输出分配和一次核启动。

## 4. 设备核

网格三维：

| 维 | 范围 | 含义 |
| --- | --- | --- |
| 0 | `1` 或 `L` | 层 |
| 1 | `ceil(R / 8)` | 每程序处理 8 个请求 |
| 2 | `ceil(C / BLOCK)` | 列块，`BLOCK ≤ 2048` |

每个程序：

1. 取本层映射行；
2. 对 8 个请求各读 `cu[r]`、`cu[r+1]`，得到计数；
3. 以 `column < count` 掩码加载 `X`；
4. 负值不进入映射寻址，结果写 -1；
5. 其余位置查 `M`，写到 `out[l, cu[r] + j]`。

每个输出位置恰好被一个程序写入一次，不存在竞争；无效尾部既不加载也不写。

### 4.1 两条映射路径

| 条件 | 路径 | 原因 |
| --- | --- | --- |
| `B ≤ 2^20` | 映射行载入 Triton 张量，寄存器 gather 复用 | 快；`2^20` 是 Triton 张量元素上限 |
| `B > 2^20` | 每个有效元素一次精确 int32 指针加载 | 映射行放不进 Triton 张量 |

快速路径把映射行拆成高 16 位与低 16 位两个张量。两部分都小于 `2^16`，float32 可以精确表示；gather 后用 `high * 65536 + low` 在 int32 里重组。这样即使 `M` 在 `prepare` 之后被改写为 `2^24+1` 这类超出 float32 尾数精度的值，输出仍逐位精确，不会舍入。

慢速路径直接对 `M[l, page]` 做 int32 加载，值域不受限制。

## 5. 精确性论证

- 快速路径：`page < B ≤ 2^20`，拆成 `high = page >> 16 < 2^4`、`low = page & 0xFFFF < 2^16`；两者在 float32 中精确，gather 不改变整数；重组在 int32 中完成，`high * 65536 + low < 2^20`。
- 慢速路径：`tl.load` 返回 int32，无浮点中转。
- 负值：掩码后写 -1，不参与地址计算。
- 空请求、`C=0`、`P=0`：网格至少为 1，掩码为空，输出为空张量，不启动核。

## 6. 生命周期与流

- `prepare` 编译一次并缓存 `CompiledKernel`；之后每次 `run` 直接调用 `compiled.run`，绕开 Triton JIT 的 Python 派发。
- `run` 通过 `triton.runtime.driver.active.get_current_stream(device)` 读取调用时的 stream，不缓存 stream、不建图。
- `run` 每次 `torch.empty` 新输出；调用方可以保留多份输出，互不影响。
- `prepared.inputs` 是可变列表，核启动时重新读取其中张量的当前指针；同形状 `set_` 后无需重新 `prepare`。

## 7. 内存

每次调用新增一份输出 `P × L × 4` 字节；核内不申请临时全局缓冲。主机侧校验副本只在 `prepare` 期间存在；`info.values` 保留 CPU 校验值供基线对照，属于提交接口的约定，不进入设备内存。

官方工程检查使用预热后的 PyTorch 活跃分配：

| 用例 | 峰值增量 | 输出 | 临时 | 基线峰值增量 | 测量前后活跃 |
| --- | ---: | ---: | ---: | ---: | --- |
| `packed_perf_small` | 9216 B | 9184 B | 32 B | 23552 B | 38912 → 38912 B |
| `packed_perf_large` | 1011200 B | 1010944 B | 256 B | 2126336 B | 654848 → 654848 B |

临时量是 Python 与分配器对齐产生的字节级开销；两组输入在双流保留 3 份输出、20 次回收后均恢复。

## 8. 上游落点与 C++ 边界

任务书 §5 指向 `xllm/core/kernels/npu/xllm_ops`。该目录现有文件全部是既有 aclnn 符号的 C++ 包装（`EXEC_NPU_CMD`），构建时链接 `xllm_ops` 库；新算子没有对应的 aclnn 符号，直接加入会破坏构建。任务书同时说明无需提供 ACLNN 自定义安装包，设备计算由 Triton Ascend 完成。

因此：

- 上游 PR 在 `xllm_ops` 下新增自包含子目录 `packed_page_indices/`，自带主机侧 C++ 构建、Triton 核、测试与自验证材料；
- 不修改 `xllm_ops/CMakeLists.txt`，不新增 aclnn 符号依赖，既有目标构建不受影响；
- 主机侧与设备侧的职责边界是：C++ 只读 CPU 副本并产出计划，Triton 只做设备计算与输出分配。

## 9. 依赖

PyTorch、torch_npu、triton-ascend、C++ 编译器、Ninja。主机扩展用 `torch.utils.cpp_extension.load` 编译，不需要额外的链接库。
